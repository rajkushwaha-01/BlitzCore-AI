# Deploying BlitzCore AI to Render

This repo has two deployable pieces:

- `Backend/` — Express + Socket.io API, talks to MongoDB and the AI providers
- `Frontend/` — Vite/React static site

You need a MongoDB database first — this app does not run one for you.
The easiest free option is [MongoDB Atlas](https://www.mongodb.com/atlas):
create a free cluster, create a database user, and under Network Access
allow `0.0.0.0/0` (or Render's IP ranges) so Render can reach it. Copy the
connection string — you'll need it below.

## Option A — One-click Blueprint (recommended)

1. Push this repo to GitHub/GitLab/Bitbucket (it's already a git repo).
2. In the Render dashboard: **New → Blueprint**, connect the repo. Render
   will read `render.yaml` at the root and propose two services:
   `blitzcore-backend` (Node web service) and `blitzcore-frontend` (static
   site).
3. Render will prompt you for the env vars marked `sync: false`
   (`MONGO_URI`, `GEMINI_API_KEY`, `MISTRAL_API_KEY`, the Gmail OAuth2
   vars, `FRONTEND_URL`, `BACKEND_URL`, `VITE_API_URL`). You can leave
   `FRONTEND_URL`/`BACKEND_URL`/`VITE_API_URL` blank for the first deploy —
   see step 4.
4. **After the first deploy**, Render will have assigned real `.onrender.com`
   URLs to both services. Go to each service's **Environment** tab and set:
   - Backend `FRONTEND_URL` → your frontend's URL (e.g.
     `https://blitzcore-frontend.onrender.com`)
   - Backend `BACKEND_URL` → its own URL (e.g.
     `https://blitzcore-backend.onrender.com`)
   - Frontend `VITE_API_URL` → the backend's URL
5. Saving env vars triggers a redeploy automatically. Once both are live,
   open the frontend URL and register an account.

## Option B — Manual setup (two separate services)

**Backend (Web Service):**
- Root directory: `Backend`
- Build command: `npm install`
- Start command: `npm start`
- Health check path: `/health`
- Environment variables: copy the keys from `Backend/.env.example` and
  fill in real values. Set `NODE_ENV=production`.

**Frontend (Static Site):**
- Root directory: `Frontend`
- Build command: `npm install && npm run build`
- Publish directory: `dist`
- Environment variable: `VITE_API_URL` = your backend's URL
- Add a rewrite rule so client-side routing works on refresh:
  source `/*` → destination `/index.html`

Set the backend's `FRONTEND_URL` to the frontend's URL once you know it,
and the frontend's `VITE_API_URL` to the backend's URL, then redeploy
whichever changed last.

## What was changed to make this deploy-ready

- Backend CORS, cookie settings, and email links now read from
  `FRONTEND_URL`/`BACKEND_URL` env vars instead of hardcoded
  `localhost` addresses (`src/app.js`, `src/sockets/server.socket.js`,
  `src/controllers/auth.controller.js`).
- Login cookie is now `httpOnly`, and `secure`/`sameSite: 'none'` in
  production — required for a cookie to survive a cross-site request
  between a separately-hosted frontend and backend over HTTPS.
- Added `app.set('trust proxy', 1)` so secure cookies work behind
  Render's reverse proxy.
- Added a `/health` endpoint, a 404 handler, and a centralized error
  handler to `src/app.js`.
- Added a `start` script (`node server.js`) to `Backend/package.json` —
  Render's default Node start command expects this.
- Frontend API/socket clients now read `VITE_API_URL` instead of a
  hardcoded `http://localhost:8000` (`auth.api.js`, `chat.api.js`,
  `chat.socket.js`).
- Fixed `chat.socket.js` not returning the created socket.
- Fixed an import in `app.routes.jsx` that referenced
  `components/protected` (lowercase) while the file on disk is
  `Protected.jsx` — this works on case-insensitive filesystems (Mac/
  Windows) but **fails the build on Render's Linux filesystem**.
- Added `.env.example` files for both apps and a `render.yaml`
  Blueprint.

## Notes / things worth knowing

- The free MongoDB Atlas tier and Render's free web service both spin
  down/sleep after inactivity — the first request after idling can be
  slow.
- Email sending (`mail.service.js`) uses Gmail OAuth2 and requires
  `GOOGLE_USER`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, and
  `GOOGLE_REFRESH_TOKEN`. Without these set correctly, registration will
  still create the user but the verification email will fail — check
  the backend logs.
- `JWT_SECRET` is auto-generated by the Blueprint. If you set it
  manually, use a long random string.
